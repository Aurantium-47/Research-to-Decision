# 调研并作出选择

## 触发名与分工

中文名称为“调研抉择”，自然语言别名为“调研skill”“调研 skill”“利弊抉择skill”。明确指定时使用 `$research-decide`；保留技术目录名，避免破坏已有引用。

- 用户要比较、排除或作决定：本技能负责需求、候选比较与结论。
- 要找现成 skill：已安装 `find-skills` 时用它发现候选；否则直接检索技能目录与原始仓库，再回到本技能比较。不要把技能市场当作通用信息搜索入口。
- 要看网友经验、原帖、评论、视频或平台资料：按需读取 `chinese-platform-research`；决策任务只委派材料搜集与证据核对，由本技能统一给结论。用户只要搜集材料时，直接使用平台技能，不强加决策流程。
- 要学术综述、领域论文地图：使用宿主已有的学术检索技能，或 BMad 的 academic-lit 研究包。复杂任务可以同时需要专业资料搜集与决策比较，只加载有关部分，不把全部流程串行跑一遍。

被其他技能调用时完成指定子任务，不再把同一任务转回调用方形成循环。

## 原版研究流程

2026-10-23 起，本入口使用已安装的 `bmad-deep-recon` 原版作为深度调研与选型的执行流程。收到深度调研、比较选型或条件推荐任务时，先读取 [BMad 接入说明](references/bmad-integration.md)，完成或检查项目配置，再读取相邻目录 `../bmad-deep-recon/SKILL.md`，按实际任务加载其 Run / Process / Refresh 和 Select 等原版参考文件。本入口下文是用户偏好与输出验收补充，不是第二套必须再跑一遍的完整流程。简单单点查询不强行启动完整研究。

不要把仅加载本入口称为执行过 BMad；实际调用、来源获取、报告和校验结果要留在当前项目中。原版安装固定于提交 `61e01f82644c4bb533750cfa0d6d61ab61d2cc9b`，属于上游 V7 Preview Alpha；保持原版文件不变，以项目自定义配置和本地补充规则适配。

目标是让用户能决定下一步，而不是罗列介绍。检索可以深入，最终输出保持中等长度、结论先行；详细证据另存当前工作区。充分使用用户已授权的研究额度，但不要以重复搜索或固定候选数量充当深入。

本入口的可检查交付标准见 [决策输出约定](references/decision-contract.md)。修改本技能或复核输出时读取。实际用户的需求来自当前对话和其授权资料，不能把示例偏好当成新用户的偏好。

## 定义要做的决定

从对话和可读取的项目资料提取用途、当前方案、硬约束、偏好及成功标准。区分已确认事实与假设。优先读取已有数据，不要求用户重复填写。只问会改变排序的缺口，通常一轮一至三个问题；等待时继续不依赖答案的工作。

主动把模糊要求转成选择题或实际例子，不把澄清完全交给用户。例如“效果好”可能指找到冷门候选、证据准确、输出易读或部署省心，应问会让首选改变的那一项；能从已有对话回答的就直接沿用。说明答案将影响什么。若答案尚未到达，按不同答案分别调研；需要该答案才能定案时保留条件，不把沉默当作确认。记录偏好时保留原话、日期和可变性。

把愿望转成可验收结果。例如，“介绍不能空泛”应转成：真实输入输出样例、谁适合/不适合、实际依赖、首选理由、最强替代方案以及什么条件下改选。

主动考虑容易漏掉但会影响选择的条件：运行平台、维护状态、总费用、数据/账号依赖、隐私、迁移退出成本、故障恢复与可替代性。只展开与当前决定有关的条件。

用户列出的要求是起点，不是完整清单。先借助现成方法、领域资料、真实使用案例、差评和替代做法，发现可能遗漏的判断标准；再用具体场景与用户讨论会改变排序的那几项。把“用户已确认需求”和“从调研提出的候选需求”分开，不用脑补把新偏好替用户定下来。优先复用成熟方案，只有现成方案留下明确缺口时才自建。

## 找候选并核实

先覆盖不同的解决思路，再深入有竞争力的候选；合格方案有几个就写几个，不凑固定三个。包括继续用现有方案或简单手工方案，若它们确实有竞争力。

### 用结果调整检索，而不只是换同义词

先说明本轮要解决的决策缺口，再为它选择检索角度，避免把用户原话直接翻译一次就停止。按题目需要使用：

| 角度 | 如何构造查询 | 能补上的缺口 |
|---|---|---|
| 实际任务与产物 | 动作、输入输出、使用人群，如“比较方案并推荐”而不只搜“research skill” | 找到名称不同但解决同一问题的工具 |
| 领域术语与相邻方法 | 从权威文档或相关结果提取术语；中英文、缩写、旧称；如 requirements elicitation、decision support、query expansion | 找到用户不知道该如何称呼的能力 |
| 替代路线 | 同一用途的插件、工作流、Agent、现有产品或人工方案 | 避免只在预设产品类别里挑 |
| 硬约束与实现 | 候选名加平台、集成、费用、数据源、文件名或真实报错；必要时限官方文档/仓库 | 核实“看起来能用”是否实际可用 |
| 反例与结果 | 候选名加限制、失败、issue、迁移、benchmark、sample output或demo | 找出不适合的场景和可验证效果 |

查询太宽时加任务、约束或限定来源；结果太少时移除可选条件、换功能术语或查相邻路线；结果高度重复时追溯原始出处、相关项目和issue，不把转载数量当独立证据。根据搜索工具支持选择精确短语或站点限定，不机械套运算符。

深入任务在工作区简记“想查什么—实际查询—发现什么—为何换角度”；只记录影响选择的检索转向。对未找到的功能写清检索范围，不能由“没有搜到”推出“不存在”。已有结果支持初选后，优先核查最可能推翻首选的缺口。

- 找技能时，可用已安装的 `find-skills` 发现候选；本工作流负责需求、比较和验收，不替换其入口、不让两个流程递归互调。
- 一般工具或方案，用当前可用的搜索、官方文档、仓库与连接器，不必经过技能市场。
- 来源按问题选择，可以组合：例如技能选型同时需要技能市场/仓库和社区使用反馈；消费、学习与生活方案可能需要小红书、Reddit、知乎、视频实测和官方规则。不是“找skill只能搜GitHub，其他问题只能搜社交平台”的互斥分流。平台技能负责实际可读的原帖、评论与媒体证据，不用搜索摘要冒充读过。
- 网友经验用于发现问题、失败案例和使用感受；关键功能、价格、限制回到原始来源核对。区分官方声称、源码显示、作者演示、本机测试与用户反馈。
- 开源项目记录仓库 URL、Star 与查询日期、维护情况；若有单项安装数，明确其统计口径。仓库热度不能归给单项功能，不能证明有效、安全或盈利；不设只凭 Star 淘汰的硬阈值。
- 阅读实际入口和代表性实现，检查安装后是否带齐引用文件和依赖。避免只复述 README 的营销句子。

深度以决策缺口是否得到解决衡量：有竞争力的不同路线得到覆盖，决定排序的能力有证据，主要反例已处理，剩余未知不再足以改变推荐时即可收敛。若成本、访问限制或时间使关键缺口仍未解决，给条件推荐并点明该缺口。不要用固定检索次数、候选数量或长篇报告冒充深入。

## 比较真正会改变选择的差异

先排除不满足硬约束的方案，给具体原因。保留候选的比较列应来自需求，而非每个项目自己的宣传分类。

每个入围方案说明：擅长的真实任务、短板、适用条件、部署/维护代价。给出首选与最强替代项，解释首选在哪些方面牺牲了什么，以及哪条新信息会改变推荐。不要把全部方案写成“都很好，各有特点”。

检查区分度：比较至少有一处能直接解释排序的“同一任务下，A能做到什么、B在哪一步不同、证据是什么、这对用户有什么影响”。避免把“功能丰富、灵活、强大、适合深度研究”等形容词当作差异；把项目名称互换后仍成立的介绍需要重写。若现有证据区分不了候选，说明最值得补查或小测的项目，不制造差异。未知不等于缺点，未找到功能不等于功能不存在。

当不同使用情景会改变结论时，按用户实际相关的情景比较，推荐程度可用“首选／有条件推荐／暂不推荐”，并分别说明理由。把推荐程度与证据把握分开：很适配但尚未实测，不能写成效果已验证。不要虚构无关情景凑表。

结论明确回答：“按你现在的情况我选谁；为此放弃什么；什么条件变化会改选谁”。若用户尚未确定关键偏好，提供简短分支，帮助其做取舍，避免把所有方案介绍一遍后把决定原封不动退回用户。

只有用户权重明确且评分有依据时才加权打分；否则用可检查的条件和明确取舍，不用虚构精确分数制造确定性。

## 适量实测

当测试可能改变选择时，对最有竞争力的候选使用同一个小任务。优先现有只读数据、公开数据或明确标注的虚构样例；不要把用户私有资料默认发送给新供应商。

演示围绕用户的真实使用过程：一个具体输入、关键输出片段或截图、它能否帮助作决定，以及最明显的一处局限。对比时保持任务与已知条件一致，说明工具、数据或额度差异；必要时增加一个会暴露短板的小案例。不要只展示安装成功或CLI帮助。无法运行时，选官方示例/录像/样例输出并标出尚未验证之处；助手手写的效果示意单独标注，不能冒充该候选的真实输出。

记录版本/提交、输入、执行命令、退出结果和可读产物。成功应证明一项实际能力，例如能读对持仓、能处理缺失数据、能给出有效金额，而不是仅证明文件存在。

需要付费账号、无法接入或不适合运行的候选，直接说明未测部分，改查官方演示、源码和可复现案例。不能把自己手写的示例称为候选的实际输出。结构校验、CLI 启动和端到端测试分别报告。

外部多模型/Agent 框架仅在实际安装、认证可用且授权允许时使用。说明哪些模型真正贡献了结果；本机额度授权不等于购买新订阅或允许向新供应商传私有数据。不可将当前模型的多角度分析称为独立多模型评审。

## 交付

默认给：明确推荐；按关键差异组织的短比较表；主要淘汰理由；一个演示或实际结果；具体下一步。可把详细候选池和证据放在本地报告并链接。用户授权安装或实施后，继续完成相应操作和验证，不停在建议阶段。

正文保持中等长度，让用户读完能行动；检索日志、源码细节和完整样例另存证据。用户只需提出任务，不必自己设计查询角度或评分表。简单决策省略无帮助的步骤，复杂决策可以深查而不把所有过程塞入正文。

承认用户已表达的偏好。只提示会改变当前决定、尚未解释的新限制；不反复加入泛泛免责段落，也不把用户的乐观判断自动写成事实。
